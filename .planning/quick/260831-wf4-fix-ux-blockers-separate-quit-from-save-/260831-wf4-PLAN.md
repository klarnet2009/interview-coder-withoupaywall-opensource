<objective>
Close four UX blockers found in the audit of the always-on-top interview overlay: Quit sitting inside the primary action group next to Save, zero confirmation on any destructive action, a dead end for users with no API key configured, and a dev toolbar overlapping the WelcomeScreen footer hint.

Purpose: this is an overlay used live, mid-interview, while the user is talking to an interviewer. A misclick that quits the app or wipes session history is not a nuisance, it is the loss of the session. The user hit the Quit-next-to-Save trap during the audit session itself. At the same time, over-confirming is its own failure — a confirmation the user cannot dismiss without reaching for the mouse is worse than no confirmation at all.

Output: a keyboard-first ConfirmDialog primitive built on the existing Radix dialog, three confirmations (quit, clear-all-history, delete-one-session) and deliberately no others, a legible forward path out of the no-API-key state, a fixed stacking bug, and an automated i18n parity gate so the 262-key en/ru symmetry stops depending on care.
</objective>

<destructive_action_classification>
The audit counted 18 delete*/clear* call sites. Confirming all 18 would be the wrong fix. The renderer-reachable destructive IPC surface, classified:

| Action | Call sites | Recoverable? | Confirm? |
|---|---|---|---|
| `deleteScreenshot` | `_pages/Debug.tsx:506`, `_pages/Queue.tsx:56`, `_pages/Solutions.tsx:688` | **Partly** — Ctrl+H (`electron/shortcuts.ts:41`) captures the display as it is *now*, not the deleted image, so it is a one-second retake only while the source is still on screen; a scrolled-away or closed panel is gone | **No** — see rationale below |
| `deleteLastScreenshot` | Ctrl+L global shortcut (main process) | **Partly** — same caveat, and the user typed a deliberate chord rather than clicking a target | **No** — see rationale below |
| `deleteSessionHistoryItem` | `_pages/Solutions.tsx:740` | No — the session and its snippets are gone | **Yes** |
| `clearSessionHistory` | `_pages/Solutions.tsx:749` | No — every session gone at once, and it is a hover-revealed button in a list | **Yes** |
| `quitApp` | `Settings/SettingsPage.tsx:1127` footer button | No — mid-interview the session is lost | **Yes** |
| `clearStore` | preload only, **no renderer call site** | n/a | **No** — nothing to gate |
| `resetWizard` | preload only, **no renderer call site** | n/a | **No** — nothing to gate |

Three confirmations, not eighteen.

Be honest about the screenshot case, because the easy version of this rationale is wrong. "Just retake it with Ctrl+H" only holds while the captured content is still on screen — the shortcut grabs the current display, not the image that was deleted, so a screenshot of a panel the user has since scrolled away from or closed is genuinely unrecoverable. The deciding factor is therefore **not** that the loss is cheap; it is frequency. Screenshot capture and deletion are the highest-frequency actions in this app, and a prompt on every one of them produces a user who dismisses confirmations without reading them — which is precisely what would make the history-clear confirmation stop working when it matters. Accepting a small, real risk on the frequent action to keep the rare, catastrophic one meaningful is the trade being made, and it should be recorded as a trade rather than as a free win.

Explicit non-goal: the **Ctrl+Q global shortcut** stays unconfirmed. It is a deliberate two-key chord, not a misclick target, and confirming it needs a main-to-renderer round trip that does not fit this plan. The audit finding was about the button adjacency, and that is what gets fixed. Flag it in the summary as a known remaining sharp edge.
</destructive_action_classification>

<dead_end_reasoning>
Finding 3's fix is deliberately NOT "enable the Save button". Saving an empty API key is meaningless — the disabled state is correct. Two things are actually wrong:

1. **The block is mute.** The button is dimmed with no adjacent text saying what is missing or where to get it. `PROVIDER_LINKS` already maps every provider to its key page and is already in scope in the file — the information exists and is simply not shown.
2. **There is no forward path, only a loop.** Cancel returns to WelcomeScreen, whose only affordance is a button back into the same settings page. Meanwhile `WizardContainer` — the guided flow that exists specifically to get a first-time user to a working key — becomes permanently unreachable the moment `wizardCompleted` is true (`src/App.tsx:139` is the only place `showWizard` is set true, and only when the wizard was never finished). The app ships with no key, so this is the literal first-run experience.

So: make the requirement legible where the block is felt, and re-open the guided path that already exists. Not a new flow, an unreachable one made reachable.
</dead_end_reasoning>
